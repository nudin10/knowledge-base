agree on the API first

A starter kit for contract driven development: OpenAPI contracts, make shortcuts, and a mock server and Swagger UI that run in containers.

github.com/nudin10/contract-repo · October 2026

The problem

Today, teams clarify the API after they build it

Clarify after building

Coding starts before front end and back end agree. Mismatched assumptions surface at integration time.

Docs drift

API docs are hand-written wiki pages, updated after release, so they're stale during the sprint.

The waiting game

With no contract up front, consumers wait for the back end to finish. Work runs in sequence, not in parallel.

Each late mismatch costs, on average
2–3 dchange and redeploy code
1 dreopen and re-review pull requests
1 dre-run tests

plus sync-up meetings and context switching. Team estimates.

The practice

Define expectations before implementation

In contract driven development, the API contract, written as an OpenAPI file, is the single source of truth.

Teams argue about the contract during design, in a pull request, instead of in chat after the code exists. Once it's agreed, everything else is derived from it, so consumers and the provider can work at the same time.

This repo

The smallest version of the practice that works

1 · Maintain

Keep contracts in git

One folder per service. Changes go through pull requests, so the diff is the design review. make lint checks them.

2 · Mock

Run a fake server

One command starts Prism on your machine, answering with the examples in the contract.

3 · Document

Browse it in Swagger UI

One command serves the contract as interactive docs on your machine.

only needsDocker or Podman. No language runtime or packages to install.
Layout

A makefile, templates and the contracts

contract-repo/
├── makefile                  # every command lives here
├── README.md
├── LICENSE · .gitignore
├── redocly.yaml              # lint rules
├── templates/
│   ├── service.template.yaml # root spec for a new service
│   ├── api.template.yaml     # starter endpoint (health check)
│   └── schemas.template.yaml # starter shared schema
└── services/
    └── example/
        ├── example.yaml          # root OpenAPI 3.1 spec
        ├── paths/
        │   └── health_check.yaml
        └── components/
            ├── components.yaml
            └── schemas/  parameters/  …

services/

The contracts. One folder per service, each with a root spec plus paths/ and components/.

templates/

What the scaffolding commands copy. Edit these to change what every new service starts with.

makefile

Scaffolding, linting, mock server and docs. Run make on its own to list the commands.

Anatomy of a service

One root file per service, one file per endpoint

services/example/example.yaml
openapi: 3.1.0
info:
  title: example
  version: 1.0.0
paths:
  /health:
    $ref: './paths/health_check.yaml'
components: {}

The root spec lists every path and points each one at its own file with $ref.

services/example/paths/health_check.yaml
get:
  summary: Health check endpoint
  responses:
    "200":
      content:
        application/json:
          schema:
            type: object
            properties:
              status:
                type: string
                example: ok  # what the mock returns

components/ holds shared schemas, parameters, responses, request bodies and headers.

Workflow

Seven make targets cover the whole loop

1
Onboard a service
make new-service SERVICE=orders
2
Add an endpoint
make new-api SERVICE=orders API_NAME=order-summary
3
Check it
make lint SERVICE=orders
4
Mock it
make start-mock SERVICE=orders
→ http://127.0.0.1:4010  ·  stop with make stop-mock SERVICE=orders
5
Document it
make start-swagger SERVICE=orders
→ http://127.0.0.1:8080  ·  stop with make stop-swagger SERVICE=orders

Run every command from the repo root. Add RUNTIME=podman to use Podman instead of Docker.

Scaffolding

The make targets write the boilerplate and wire it up

make new-service SERVICE=orders
services/orders/
├── orders.yaml   # template, title set to "orders"
├── paths/
│   └── health.yaml  # /health, mockable right away
└── components/
    ├── components.yaml
    ├── schemas/       parameters/
    ├── responses/     request_bodies/
    └── headers/
make new-api SERVICE=orders API_NAME=order-summary
paths/order-summary.yaml  # copy of api.template
orders.yaml               # gains the path:
  /order-summary:
    $ref: './paths/order-summary.yaml'
Your part
  • Replace the copied health-check body with the real endpoint.
  • Run make lint SERVICE=orders before you open the pull request.
Guard rails

Both commands stop with a clear message if SERVICE or API_NAME is missing, if the service doesn't exist yet, or if the file already exists.

Mock and docs

Run the contract before anyone writes the service

start-mock runs
docker run -d \
  -p 127.0.0.1:4010:4010 \
  -v $PWD/services/orders:/spec \
  --name mock-orders \
  stoplight/prism:5 \
  mock -h 0.0.0.0 --multiprocess=false \
  /spec/orders.yaml
$ curl localhost:4010/health
{"status":"ok"}

Prism answers with the example values in the contract.

start-swagger runs
docker run -d \
  -p 127.0.0.1:8080:8080 \
  -v $PWD/services/orders:/oas \
  -e SWAGGER_JSON=/oas/orders.yaml \
  --name swagger-orders \
  swaggerapi/swagger-ui:v5.29.4
  • The service folder is mounted, so $ref files resolve.
  • Both bind to 127.0.0.1, so they're reachable only from your machine.
  • Containers are named per service. To run several at once, give each its own PORT and UI_PORT.
Settings

Settings are plain make variables

VariableDefaultUsed by
SERVICErequiredevery target except help
API_NAMErequirednew-api
RUNTIMEdockerlint, start / stop targets · or podman
PORT4010start-mock
UI_PORT8080start-swagger
PRISM_IMAGEstoplight/prism:5start-mock
SWAGGER_IMAGEswaggerapi/swagger-ui:v5.29.4start-swagger
REDOCLY_IMAGEredocly/cli:2.60.0lint
SPEC_DIRservices/$(SERVICE)lint, start-mock, start-swagger
make start-mock SERVICE=orders RUNTIME=podman PORT=4011
