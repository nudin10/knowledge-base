Unstructured context: an agent with no memory builds on whatever it finds, and guesses the rest with full confidence.

So where should each kind of context live?

I want to start with a failure, and the mechanism behind it. An agent starts every session with no memory, so it builds its picture of the task from whatever context it finds nearby: local files, leftovers on the branch, a draft that looks like a brief. If the real source is not where it looks, it infers the rest and builds on that guess with full confidence. Here is the real case. An agent was asked to complete a set of APIs on a branch. It looked at what was local: two database migrations that nothing used yet, and a draft document in the docs folder whose rules matched one of them. It read like a brief. The agent started to build, edited two files, and then had to revert both. The real scope was a page in the team docs, which live in Lark, and a person had to supply it, and that page described a different feature. The code it wrote was not the problem. It was confident, consistent work on the wrong thing, because the right context was not in the session. So the question for this talk is: where should each kind of context live, so that the right piece is in front of a person or an agent at the right time?

Each layer has one job and one audience. Lark is read by humans and by agents, so it has the highest bar for quality. The code is what is actually built, and I check it against Lark. The code and the doc will disagree sometimes. When they do, one of them has to be the reference. If it is the code, every bug quietly becomes the spec, and nothing is left to argue with. With the team docs as the reference, a mismatch becomes a question: is the doc wrong, or the code? Either answer is a fix. The doc earns that place for a few reasons. It holds intent: the designer drafts the design there first, and the code is one attempt at it. A check has to sit outside the thing it checks; code cannot tell you it is wrong, and tests only tell you it matches the tests. And with agents, code is cheap: a feature is rewritten in an hour and branches are rebuilt all week, while the doc changes slowly, under a person's review. When building gets fast, deciding what to build is the slow part, so that is what gets anchored. It also outlives any one person, and it answers questions without anyone having to ask the author; other teams, product people and an agent with no memory can all read it. The limit is real. The team docs say what should happen; only running code says what does. Each is first for its own question, which is why the next slide ends with running it. The footer is the price: a stale doc is worse than none, so it changes in the same PR as the code. How it stays usable: it holds the current contract with no history, it is written in plain English, agents edit one block at a time, and the tools use the user's own login.

When the layers agree, trust them by default. When they disagree, you know exactly where to look.

The rare case where they agree and are both wrong is what running it catches.

Inside Lark there are several documents that describe the same system from different sides: the API contract, a resource doc, the data model and the load-test results. They must agree with each other, and they must agree with the deployed code. When I check consistency, I compare the documents with each other first. This found a real drift: an event in the API contract still used old field names, such as storeId, while the resource doc and the code had moved to storeIds. It had been wrong for months. Nobody found it by reading the code. It showed up because two documents disagreed. So consistency is the everyday check, and the main signal I use for judgement: it is cheap, it runs all the time, and when two layers disagree it points at the exact place to look. Its one blind spot is a gap the layers share: if they agree and are both wrong, nothing disagrees. That rare case is why the deck also runs things, and the next slide shows one.

The vault is an Obsidian vault of short notes about decisions. Decisions are recorded when they matter, which depends on someone remembering to do it, and recalled before acting. It is a record of reasoning, not documentation of the current state. Two real examples. The first is the note from the opening story; the rule that came out of it is to ask for the source document before writing code, if it is not in context. Connected context is robust context.

Every reference I write is a real link: the pull request URL instead of a bare number like #1234, the Lark wiki link instead of "the API doc", the Jira issue link instead of "the ticket", and commit links. A link can be followed by a person or by an agent. A bare number or a name cannot: the reader has to guess which repository, which page, which ticket. On the map, the links tie the layers together: a Lark page points to the PR, the PR points to the Jira issue, the vault note points to both. The note on the right has the same information as names only, and nothing in it can be followed. Connected context is robust context.

“Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.” Hunt and Thomas, The Pragmatic Programmer

The long explanation lives once, in Lark. Code comments, PR descriptions and Jira tickets stay short and link to it. They do not explain it again. When the same paragraph is pasted into a PR, a comment and a ticket, the three copies drift apart as each one is edited on its own, and a reader cannot tell which one is right. With one Lark section and three short links, there is nothing to drift. The structure also carries meaning: where a piece of writing lives tells the reader what it is. A Lark page is the contract, a PR body is the change, a vault note is the reason. This is the DRY principle from Andrew Hunt and David Thomas, The Pragmatic Programmer, Addison-Wesley, 1999: "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." It also matches the Diátaxis framework by Daniele Procida, which keeps explanation and reference apart.

Fix the shape, and the intermittent bug stops being intermittent.

Make illegal states unrepresentable. Yaron Minsky

Why do I still spend time on refactors? Because many bugs we call transient, intermittent or unexplainable are structural. A flaky symptom usually means the structure allows two orders or two paths, and nothing makes one of them impossible. Two real cases. One: every write was refused, even on an idle service. A concurrency limiter ran after the auth middleware, so a client that left during auth took a slot that was never released. The fix skips a request that is already closed and makes the middleware order explicit; the code line on the slide is the real guard. Two: reads were slow only under load. Each query checked out its own pool connection, sometimes while it held another, which is hold-and-wait, and one read made 20 pool checkouts. The fix is one connection per unit of work, through a held-connection scope. In both cases, a refactor that makes only one order or path possible removes the whole class of bug, not only the case we saw. The same pattern shows in test flakiness: Luo, Hariri, Eloussi and Marinov, "An Empirical Analysis of Flaky Tests", FSE 2014, studied 201 commits that fixed flaky tests in 51 open-source projects and found async waits, concurrency and test order dependency to be the most common root causes. The same idea is Yaron Minsky's "make illegal states unrepresentable", from his Effective ML talk and the Jane Street blog post of the same name, 2010: if the structure cannot express the bad state, nobody has to remember to avoid it. A fix moves up the stack only if the next PR would conflict.

Larger work ships as a stack of pull requests. Each PR is based on the one below it, and the bottom one is based on staging: staging, then PR 1, 2, 3 and 4. Smaller, independent changes go straight onto staging as side PRs. When a fix lands in the middle of the stack, I do not push it up through every PR by habit. I move it up only if the next PR would conflict without it. A clean rebase does not need a cascade, and every extra push restarts CI and review for nothing.

When rebasing is cheap and provable, keep history linear.

History stays a straight line. There are no merge commits, not even on local throwaway branches. When a review finds a problem, the fix does not become a new commit on top: I create a fixup commit for the commit it belongs to and autosquash it in, with the two commands on the slide. A deploy branch is one snapshot commit on top of staging, and its patch-id matches the stack. Teams used to choose merge over rebase for a practical reason: a rebase made a person untangle conflicts commit by commit, often the same conflict again and again. That cost has changed, and here is the evidence. Four commits were ported into a different code layout: an agent resolved each conflict in the context of its commit, and the full test and database suites passed. That is the real test. Eight commits were replayed onto a newer base, and git range-diff showed all eight unchanged; that means there were no conflicts, which is the easy case. And a fix was folded into a commit six commits back: all six later commits kept identical patch-ids, and the final tree differed by exactly the 23-line rule. Patch checks prove that the replay changed nothing; only tests prove that it is right. When rebasing is cheap and provable, keep history linear.

One push at a time, and each PR’s CI must finish before the next: a stack of PRs pushed together would run every CI at once and hog the shared runners.

Before anything is pushed, it goes through the same sequence. First the local tests, including the suites that run against a real database. Then typecheck and lint. Then a local SonarQube scan on the changed files, so the quality gate does not fail after the push. Then a review: an agent drafts the findings, and a person judges them. Only then the push, and CI runs. A clean build alone is not enough. And I do this for one PR at a time: the next PR starts the sequence only when the current one is through. The CI runners are shared by the whole team, and a cascade push starts a full CI run for every PR in the stack at once, so waiting keeps the runners free for everyone. Waiting also means I read each result before the next change goes out.

The human part of this work is judgement. It starts with design: the data model, the API contract and the event design are drafted by a person first, and agents polish and build on that draft. Then hunches. Later, after the harness fixes, "the improvement is significant, I'm a little suspicious" led to cross-checking the k6 counts against the server logs: 2,497 and 7,404 matched, and the numbers held. The rule anyone can use: a result better than expected is a reason to check the tool, not to celebrate. Another hunch, "the slide is still buggy", found a layout bug that only shows at one screen size. Then technical calls that changed the shape of the system, which no tool made on its own. Services that ship in one deploy do not need a network hop between them, so the module exposes an in-process SDK with one entry point. One import direction, enforced by lint, including the rule that other modules only import the SDK entry. A missing scope must never mean everything, so the scope has an explicit "all" value, and a value that someone left out cannot widen a record. Measure where the code runs: the same spec on staging measured the real cost, which local tests could not. No golden fixture tests, because they drift silently; contract tests and real Postgres suites instead. Agents run the tools, the tools produce the evidence, and people judge. Choosing which question to ask, and noticing that something feels wrong before anything has failed, is still the human's job. It looks random, but it is experience pattern-matching on signals that are not written down anywhere.

Appendix: what you need to try this. This is the toolkit that connects each layer to a session. For Lark, lark-cli reads and writes docs and wikis with my own user-delegated login and no scope elevation, the lark skills tell a session how to use it, and a Lark agent does Lark work in the background. For Jira, the Atlassian MCP connector reads and writes tickets in markdown, and tracking uses Jira's own epics, links and status. For the code, gh with gh-stack manages stacked pull requests, each PR gets its own git worktree, local SonarQube scripts run the quality gate before a push, and kubectl and gcloud reach staging. The load-test harness sits beside the code: k6 locally and in the cloud, with Grafana, Jaeger and Pyroscope to read the results. For the vault, the Obsidian CLI reads and writes notes, and a vault agent helps record decisions when they matter and recall them before acting. Memory is the agent's file-based memory: an index with one fact per file. The team skills pack is shared and versioned. It teaches a session the company systems: an architecture overview, logs, databases, metrics and code quality. The rule across all of them: auth is always my own, and never elevated.
